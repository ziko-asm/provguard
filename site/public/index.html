LLM agent security · open source

Untrusted data must not steer what your agent does.

ProvGuard sits between an LLM agent and its tools. It does not try to spot malicious text. It checks where every sensitive argument came from, and refuses the call when only an outsider supplied it.

    Written blind, fixed in the open

    The four policies were committed before any injection task was read and have not changed since. The first run exposed one real flaw: in Slack the attack text sat inside a channel name, and the channel list was trusted, so a URL inside that name looked trusted too. v2 changed the library, not the policies. Structured tool output now vouches only for complete field values, such as the channel general, never for text found inside a field.

    What still gets through

    • Attacks that pick among options that are legitimate anyway: book the priciest hotel in the real catalogue, delete a file id from the user's own list.
    • Data sent to a recipient the user really named, inside the message body.
    • Writes with no sensitive argument, such as a calendar event with no guests.

    Argument provenance cannot stop these by design. Confirmation on state-changing tools moves them to a person. The benchmark has no person, so the gap is reported instead of hidden.

    A live agent

    Qwen3 8B running locally: every user task of a suite, and its first three injection tasks against each of them. One run per defence at temperature 0.7, so small differences in utility are noise. Banking uses the blind v2 policy; Slack uses the v3 policy with no person present, so every confirmation counts as a refusal. Across both suites ProvGuard let 0 of 111 attacks through, against 30 of 111 without it; on its own, 0 of 63 on Slack bounds attack success below 5.7% (95%).

    The price shows on Slack: with nobody to approve confirmations, clean utility falls from 71% to 43%. The replay above estimates that a person who approves the legitimate confirmations recovers 20 of 21 tasks; that has not yet been measured with a live model.

    v0.2 · what the first evaluation taught

    Closing the gaps it reported

    The first evaluation listed what still gets through. v0.2 answers each item with a narrow, testable rule, and changes how attacks are scored so the numbers cannot flatter the guard.

    • Links inside free text

      urls: trusted checks every link in a message body. An attacker can no longer hide www.evil.example in a note to a real colleague.

    • Secret fields stay home

      secret: [passport_number] marks fields that must never appear in outgoing text. Values the user typed themselves are still theirs to send.

    • Approve once, not forever

      guard.grant() lets one argument take one approved value, or values from one named source, and counts down. "Pay the bill in this file" works without opening every payment.

    • Numbers by value

      240, 240.0 and 1,000 match their trusted fields. A digit inside a decimal no longer counts as evidence, and min_length rejects values too short to prove anything.

    • Scored by outcome

      An attack now counts as stopped only if AgentDojo's own check says its goal was not reached, reported twice: with confirmations refused, and with every confirmation approved. Pairs the replay cannot judge are counted apart, with exact 95% intervals.

    • A guard that knows it is watched

      A new provenance_aware attack tells the model about the filter and asks it to launder values. The harness can also run AgentDojo's DeBERTa injection detector as a baseline, the approach ProvGuard argues against.

    The blind numbers hold. Rescored by outcome, no attack that v2 counted as stopped reached its goal. With the v3 policies, and a person who refuses suspicious confirmations, every replayable attack in all four suites is prevented, and Slack solves 20 of 21 tasks instead of 12.     Mechanism

    How a decision is made

    1. Label every input

      User and system messages are trusted. Tool output is untrusted unless the policy says nobody else can write into it.

    2. Trace each argument

      Before a tool runs, each argument value is matched against the labelled inputs: whole tokens, case and spacing ignored.

    3. Require a trusted origin

      A protected argument passes only if a trusted source contains it. Values from e-mails, web pages, or the model's imagination fail closed.

    4. Escalate when tainted

      Once untrusted text is in context, sensitive tools can require confirmation or be blocked outright.

    version: 1
default:
  on_tainted: confirm      # unknown tools never pass silently
tools:
  read_inbox:
    output: untrusted
  get_contacts:
    output: trusted
  send_email:
    on_tainted: confirm
    args:
      to:
        require: trusted
        on_violation: block

    Limits, stated up front

    • Provenance is value matching, not token-level tracking. A value that a trusted input happens to contain will pass.
    • Free text is checked for links and marked secret fields only. Data the model paraphrases, or that no policy marks as secret, can still leave in a message body.
    • The guard only knows what it is shown. Input that bypasses it is invisible to it.
    • Under strict policies, tasks that delegate a choice to untrusted content ("pay the bill in this file") need confirmation.
    Use it today · no code changes

    Put it in front of any MCP server

    provguard-mcp wraps an MCP server over stdio. Your client starts the proxy instead of the server, and every tool call passes the policy first. Blocked calls come back as ordinary tool errors; calls that need confirmation are put to you through MCP elicitation.

    {
  "mcpServers": {
    "files": {
      "command": "provguard-mcp",
      "args": [
        "--policy", "policy.yaml",
        "--audit", "provguard.jsonl",
        "--", "npx", "-y",
        "@modelcontextprotocol/server-filesystem",
        "/home/me/docs"
      ]
    }
  }
}

    What it can and cannot see

    • It sees every tool call and every result, and labels results by the policy.
    • It never sees your own chat message. Values you typed are trusted through --trust, a trusted tool such as your contacts, or an allow list; anything else that a policy protects needs your approval.
    • A client without elicitation support gets a refusal instead of a prompt: it fails closed.
    • One proxy guards one server. Text from other servers in the same client is invisible to it.
